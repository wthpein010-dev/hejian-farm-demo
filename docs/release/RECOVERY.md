# 播种操作冷启动恢复

2026-10-27。当前仅开发沙盒；全部验收使用合成账户和临时数据库。新协议用于播种固定操作参数，未把它当作财务、农友、论坛或真实设备的完整恢复方案。公开Pages仍为内存H5，不部署生产API。

## 用户体验

每次登录先检查服务端待核对操作。检查未完成或失败时，用户可读资料，暂不能提交新操作，并有明确重试入口。登录回复提供环境标识，客户端严格核对后续快照和恢复回复，不将缺字段默认成开发环境。

准备记录在服务端，客户端不把会话token、原操作编号、参数或社区正文写入storage、URL或日志。应用被关闭后，重新登录能找回当前未确认的播种意图。

- 尚在准备阶段：显示原动作、对象和时间，由用户选择继续或放弃；登录/普通核对不会自动执行业务。
- 原操作已有结果：显示原回执的动作、结果和时间；当前订单进展可以不同。确认这条结果后才解除恢复项，不把最新订单冒充原操作。
- 原结果确认回复丢失：只按原intentId重试确认，不重新执行播种操作。
- 从备份恢复的可疑准备：显示需农场人工核查，不能用户自助继续、确认或解除。

正常完整提交仍是一次明确确认：准备→执行→呈现原结果/独立读取当前进展→确认原回执。正常页面已呈现时可自动发送最后的确认；其回复不明就保留恢复提示。冷启动读到原结果要求用户明确“已核对结果，继续”。确认是账户级的客户端接受回执，不等于证明每个设备或每个人都已看过。

## 原意图与当前状态

`shared/recovery.mjs`唯一拥有严格wire，`services/api/src/recovery.mjs`拥有schema9三表（epoch、账户槽、播种意图）、固定索引、状态、校验与恢复变换。原播种业务仍由`planting.mjs`执行。Store外层IMMEDIATE事务包含业务变化、原命令账和intent终结；不能只提交其中一部分。

每个账户/环境最多一条open意图。prepare携带服务器epoch和槽版本，先查已接受的原prepare墓碑，再比较当前空槽；迟到的旧prepare即使在旧回执确认后到达，也只能恢复旧对象，不会创建新单。不同命令争用同一代际只有一个成功。

服务端生成`intent-<32hex id>`原操作编号。旧播种接口先查原账；无原账的raw请求不能用保留编号创建回执，避免先写错误参数毒化真实意图。只有服务端验证过的当前owned prepared上下文能首次执行。其他raw新编号在有open意图时明确记账拒绝`INTENT_PENDING`，此旧拒绝以后不变；原历史回执仍优先回放。prepare分配id也避开迁移前已有的同账户编号。

execute按原id/参数/时间和当前权限/业务版本执行一次。settled重试只回原回执；abandoned不执行。ack按精确原id关闭，旧ack不能清掉另一个较新的槽。abandon与execute竞争时，若已执行就回原settled结果，不谎称未执行。

## API

相对`/api/v1`，沿用会话、正文限制、慢正文后再认证、来源限流、no-store和脱敏路由模板。

| 路由 | 行为 |
|---|---|
| `GET /account/recovery` | 当前恢复检查，不触发执行 |
| `GET /account/recovery/intent/{id}` | 本人精确原对象，含已关闭对象；跨户与缺失一致404 |
| `POST /account/recovery/prepare` | 冻结原audience/command，按epoch/版本准备 |
| `POST /account/recovery/execute` | 按精确intentId执行或回放原结果 |
| `POST /account/recovery/ack` | 仅确认精确已settled原对象 |
| `POST /account/recovery/abandon` | 放弃尚未执行的原对象，竞争已执行则回原结果 |

精确字段及枚举以shared模块为准。prepare明确拒绝必须是合法同账户结果及匹配原attempt；通用HTTP错误不等于原操作失败。每个修改回复区分本次原target与当前槽id，不能错把当前新槽当旧确认凭证。

## 客户端与账户

恢复检查是独立闸门，原对象复用唯一pending槽。其他域已有未知请求时先保留其原key，不覆盖为第二个命令；核对原请求后再读取服务端open意图。401仍只能原账户恢复，换账户和迟到回复不得污染新会话。发现当前详情读取失败也能查看/确认原回执，不因读失败重发业务。

意图/槽变化撤销本人未用注销准备；有open意图先处理再注销。准备阶段未产生订单也不能绕过此保护。关闭后继续遵守原active作业限制，注销删除本人恢复槽与意图。金融Snapshot/revision、资产、奖励和原财务回执不变。

这是新播种协议的恢复保障。旧单步接口只保留开发兼容，新客户端不自动降级；其他域在另一设备上仍按其原协议运行。客户端全局闸门不等于服务端跨设备全域锁，其他域的内存pending跨杀进程恢复仍未完成。

## 备份与灾备边界

严格备份支持schema2–9，共用固定DDL/列/主外键/索引和内容校验。schema9检查账户槽、原prepare指纹、合法phase/时间、原回执与planting_commands字节一致。私有工具显式保留已完整验证的旧schema7/8，HTTP正常启动升级9。

恢复仍清会话/注销准备、禁用播种计划并撤销人员授权；另外轮换epoch、每槽版本递增，把open prepared隔离为quarantined，保留settled原回执。旧epoch无原墓碑的迟到准备不能成为新操作。隔离项不自动执行，不因重新授权而复活。

快照外丢失的操作仍必须与外部最新订单、现场作业和撤销/删除记录核对。当前未提供quarantine用户自助解除，也没有以“关闭提示”伪造原命令结果。生产恢复保持隔离直至人工灾备核查，不把本模块宣称为跨任意回滚点的完整防重。意图/命令墓碑仍增长，保留/容量和可信运维证据仍待验。

实际命令、RED→GREEN、浏览器范围与发布回执保留在`.scratch/cold-start-recovery/`；正式上线目标继续未完成。
