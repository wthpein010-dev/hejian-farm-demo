# HTTP 服务运行与诊断

要求 Node.js ≥24.15.0。此工程具备本机健康、诊断与关停检查；实际生产主机、HTTPS/代理、采集告警、容量及切流尚未验收。它们与平台登录、农场设备、支付履约及官方审核分别验证。

## 启动与探针

按[API说明](README.md)配置环境后运行 `node services/api/src/server.mjs`。服务不会自动加载 `.env`，生产秘密由部署系统或私有环境文件管理，不写入前端、仓库、URL或日志。

| 入口 | 含义 |
|---|---|
| `GET /livez` | HTTP进程可响应，不访问业务数据库或业务时钟 |
| `GET /readyz` | 数据库必需时钟记录可读、服务未处于排空；不满足返回503 |
| `GET /healthz` | 兼容原入口，按readyz语义检查；健康时保持 `data.status: ok` |

探针在业务请求限流之前处理，避免正常限流触发健康误重启；来源校验仍保留。负载均衡探针通常不带Origin，浏览器调用则必须使用配置的允许来源。健康回复没有数据库路径、用户、密钥或平台配置。

这些入口不执行完整性扫描、资产写入、实际设备或平台SDK请求。健康200只证明对应HTTP/只读存储检查，不能据此判断数据库所有写入、真实农场或整个产品已经可以上线。备份的完整性校验另见[BACKUP.md](BACKUP.md)。

## 可信代理与来源限流

未配置时只使用直接socket地址，任何`X-Forwarded-For`、`Forwarded`、`X-Real-IP`都不改变限额。反向代理部署后，可在服务器私有环境配置`FARM_TRUSTED_PROXY_CIDRS`，逗号分隔最多32个经过现场核实的IPv4/IPv6地址或CIDR。不能写域名、通配、`/0`、带端口／区域ID的值或含主机位的CIDR；IPv4-mapped IPv6配置因语义歧义被拒绝，请使用普通IPv4网络。此配置不是客户端环境变量，也不会自动信任loopback或私有网段。

仅直接peer命中配置时才解析唯一`X-Forwarded-For`。支持裸IPv4/IPv6逗号链，最多32个地址与2048字符；重复字段、空值、端口、括号、引号或无效地址固定返回400，不回显输入、不记地址日志。没有该字段时仍使用peer。IPv6等价拼写和IPv4-mapped请求地址归一到同一桶，不能用拼写切换绕过限流。`Forwarded`与`X-Real-IP`始终不参与身份选择。

完整链先做有界格式校验，再从直接peer向左越过可信代理，到首个不可信地址即停止；其左侧附加的地址不能影响限额。解析出的同一地址用于业务和登录限流。健康探针及跨域预检保持原规则。

部署方须限制后端直连、让入口代理清理外部转发头并按真实链正确追加。只加入真实代理地址，不能把所有客户端所在网段列为可信。变更拓扑时重新核验，不能以固定跳数推断安全；经多级负载均衡的链需逐级确认。现有代码不验证生产TLS、网络ACL或代理配置，也不提供跨实例共享桶，边缘限流和多实例策略仍需部署验证。

## 结构化诊断

实际CLI向标准输出写JSON行。请求事件包含服务器生成的requestId、固定路由模板、规范化method、status、completed/aborted和单调时钟durationMs；生命周期事件记录listening、draining、forced、stopped或启动失败类别。

日志不记录原URL/query、请求头/正文、IP、账户标识、会话或注销凭证、平台code、SQL及异常原文。任务/成就路径中的对象ID归为固定模板；未知路径归unknown，输入不会无限扩展标签。可用返回的X-Request-Id关联诊断记录。

标准输出sink限制待写字节，积压或故障时丢弃诊断而不无限排队，也不让日志异常改变账户事务结果。诊断为尽力记录，不是财务/设备执行回执或可靠审计队列；输出受阻可能丢日志，生产必须配置受管采集、轮转、保留、权限与告警。

嵌入 `createApp` 时可传入可信的 `logger(event)`；默认不向嵌入者输出日志。`app.metrics()`提供只读副本，包含有界路由/方法/状态/结果计数、活动请求和固定延迟桶。没有新增无授权公网metrics入口；实际采集端、访问控制与告警接收者仍由生产部署确定。

## 排空与关停

`app.close()`重复调用共享同一完成Promise。排空时新业务503，已接受的请求按正常规则处理；超过 `FARM_SHUTDOWN_TIMEOUT_MS` 后中止未完成连接与身份核验，最后关闭存储。默认10000ms，允许100–60000ms。

关闭连接只代表回复被中断，不能据此判断资产事务没有提交。客户端必须使用原正文、原版本和原幂等键核对结果；不能换新key再扣款。Node的同步SQLite或事件循环阻塞可能延迟信号开始处理，配置期限从关停逻辑被调度执行时计；宿主进程监督器仍需配置独立的最终停止期限。

实际CLI处理SIGINT/SIGTERM，启动配置或监听失败退出非零。Windows的 `process.kill` 不能模拟可捕获的POSIX信号；两项真实信号回归在Windows明确跳过，在Linux CI运行。不要把跳过记录写成已通过信号验收，也不要直接把跨平台编译当运行证据。

本轮实际修复：外部SQLite写锁曾让100ms关停配置拖至约5.6秒；排空期改为连接级零锁等待、强制中止后的身份分支不再写库后，锁竞争回归约135–145ms完成。DNS延迟监听也曾在close后打开端口，现已取消未完成的原生监听。上述为测试条件中的结果，不是操作系统实时保证。

## 持续业务验证

[LOAD-TEST.md](LOAD-TEST.md)中的工具只创建自己的临时loopback服务和SQLite。它验证真实兑换、并发重放、版本竞争、连续读写及重启资产，不会向已有服务或真实用户压测。

```powershell
node --test services/api/test/operations.test.mjs
node services/api/tools/load-api.mjs --duration 120 --workers 4
```

仓库提供手动触发的 `.github/workflows/api-load.yml`，在Linux新建临时服务运行同样的120秒业务负载，并检查实际持续时间、资产验证、错误数和清理结果。它不访问生产地址，不定时执行；脱敏数字报告作为工作流附件保存。

实际时长、请求数、错误、时延和RSS/event-loop结果以本次脱敏报告为准。本机同进程、固定节奏、临时提高限流的负载不能证明生产最大吞吐量或长期无泄漏；生产还须按核定的用户规模、SLA、TLS/代理、磁盘、备份竞争及真实外部服务重新测量。
